# Mesh Shape Discovery

AutoParallel historically requires users to pass a concrete `DeviceMesh` before
optimization.  The trace is mostly mesh-shape independent, but placement option
generation, communication costs, and the ILP are mesh-specific.  Those steps grow
quickly with `mesh.ndim`, because many operators enumerate placement choices
across every mesh dimension and the ILP expands producer/consumer strategy
products.

The discovery path is therefore not an exhaustive factorization search.  It is a
semantic, topology-aware search:

1. Trace the model once.
2. Generate a small set of semantic mesh probes.
3. Rank those candidates with cheap graph-shape signals.
4. Run the exact optimizer only on retained semantic candidates.
5. If the full 3D/4D optimizer is expensive, cap the search with ranking or run
   high-rank candidates only after 1D/2D probes identify useful roles.

This treats LP/ILP as the baseline evaluator, not as the pruning mechanism.

## Semantic Axes

The current no-PP design recognizes these roles:

- `dp`: data/FSDP axis.  This axis can cross nodes because FSDP-style
  all-gathers/reduce-scatters are prefetchable or overlap-friendly.
- `tp`: tensor-parallel axis.  This is a high-frequency, explicit communication
  axis and should fit inside a fast topology tier.
- `cp`: context-parallel axis.  This also has explicit activation exchange and
  should be node-local unless the model is specifically designed for cross-node
  context exchange.
- `ep`: expert-parallel axis.  Token dispatch/combine all-to-all is heavy, so EP
  is treated as node-local by default.

The semantic generator emits:

```text
(N,)                              # 1D DP/FSDP baseline
(N / axis, axis)                  # one node-local semantic axis
(N / (a*b), a, b)                 # two node-local semantic axes
(N / (a*b*c), a, b, c)            # three node-local semantic axes
```

The non-DP axes are always rightmost.  Their product is capped by
`gpus_per_node`, which guarantees each heavy axis remains intra-node under the
rightmost-is-innermost NCCL topology convention.  The remaining leftmost `dp`
axis is `N / product(non_dp_axes)` and may cross nodes.

## Candidate Generation

`generate_dp_tp_mesh_candidates()` is the narrow DP/TP helper.  It emits `(N,)`
and `(N / tp, tp)` for divisors of `N`, capped by `gpus_per_node`.

`generate_semantic_mesh_candidates()` generalizes this to role probes:

```python
candidates = generate_semantic_mesh_candidates(
    total_gpus=64,
    gpus_per_node=8,
    semantic_axes=("tp", "cp", "ep"),
    max_ndim=4,
    max_axis_sizes={"cp": 4},
)
```

For `world_size=64`, `gpus_per_node=8`, and `semantic_axes=("tp", "cp", "ep")`,
the generated high-rank shapes include:

```text
(16, 2, 2)     ('dp', 'cp', 'tp')
(8, 2, 4)      ('dp', 'ep', 'tp')
(8, 2, 2, 2)   ('dp', 'ep', 'cp', 'tp')
```

Different semantic mappings can share the same numeric shape.  They are kept as
separate candidates because constraints and placement interpretation are keyed by
`mesh_dim_names`.

`generate_2d_semantic_mesh_candidates()` is a compatibility helper for the
earlier first-stage-only behavior.

## Ranking Heuristics

The ranking heuristics are model-agnostic and come from tensor metadata:

- TP score: large non-batch tensor dimensions that are divisible by the TP size.
  The score uses a small synchronization-depth penalty so capped searches prefer
  the useful TP elbow instead of blindly choosing the largest intra-node TP.
- CP score: large middle tensor dimensions that are divisible by the CP size.
  This captures sequence/context-like dimensions without depending on module
  names.
- EP score: rank-3+ tensors with a leading expert-like dimension divisible by
  EP.  This is only a candidate ranking signal; dynamic MoE dispatch should
  still be expressed with `local_map` or custom operators.

The 1D baseline is always retained when candidates are capped.  The exact
optimizer still decides the final sharding strategy for every retained mesh.

Boundary constraints should be generated by mesh dim name, not by hard-coded
axis index.  For example, LLaMA logits can shard batch on `dp`, sequence on
`cp`, and vocab on `tp`:

```python
x_sharding = make_axis_placement(candidate, {"dp": 0, "cp": 1})
out_sharding = make_axis_placement(candidate, {"dp": 0, "cp": 1, "tp": 2})
```

## Exact Evaluation

`search_mesh_candidates()` evaluates candidates in order:

- creates a fresh `DeviceMesh`
- sets the NCCL topology config for that mesh
- clears mesh-sensitive placement/communication/compute caches
- builds a fresh `ShardingOptimizer`
- applies candidate-specific input/output/memory constraints
- solves the ILP and records objective, cost breakdown, build time, and solve
  time

The best optimizer is retained so placements can be exported.

## 3D+ Cost Control

If 3D/4D sharding optimization is fast enough, run the exact evaluator directly
on these semantic candidates.  If it is still expensive, avoid full
factorization and use this progressive schedule:

1. Use 2D probes to identify at most two useful heavy axes.
2. Generate only local mixed candidates whose heavy-axis product fits in a node.
3. Restrict placement options by operator family:
   - dense/mm: DP/FSDP plus at most one TP-like feature axis
   - attention: batch/head/context templates
   - MoE/local_map: DP/EP token and expert templates
   - pointwise/view/residual: inherit-neighbor or stable replicated templates
4. Run exact solve on those template-restricted candidates only.

This keeps each operator's active axes bounded even when the physical mesh has
three or four dimensions.

## LLaMA3 1B Result

Measured with the native full LLaMA3 1B-width model (`1.24B` tied-embedding
parameters), fake process group, H100 topology, `world_size=64`,
`gpus_per_node=8`, global `batch_size=64`, `seq_len=2048`, bf16 params and fp32
gradient reduction.

Command:

```bash
PYTHONPATH=. python examples/search_llama3_1b_mesh.py \
  --world-size 64 \
  --gpus-per-node 8 \
  --batch-size 64 \
  --seq-len 2048 \
  --semantic-axes tp \
  --max-mesh-ndim 2 \
  --allowed-tp-sizes 1,2,4,8 \
  --output-json /tmp/llama3_1b_mesh_ws64_after_semantic.json
```

Graph tracing took `5.86s`.  Candidate order after cheap ranking was TP=4,
TP=8, TP=2, then the 1D baseline.

| Mesh | Mapping | Objective | Build | Solve |
|---|---|---:|---:|---:|
| `(16, 4)` | `dp,tp` | `57974.2` | `32.61s` | `27.86s` |
| `(8, 8)` | `dp,tp` | `58079.1` | `29.60s` | `28.05s` |
| `(32, 2)` | `dp,tp` | `58571.1` | `28.84s` | `35.38s` |
| `(64,)` | `dp` only | `59417.0` | `1.81s` | `0.58s` |

The best candidate was `(16, 4)`: the `tp` axis is intra-node with 4 ranks, and
the `dp` axis spans 8 nodes with 2 ranks per node.

Topology derived by the NCCL cost model:

```text
mesh_shape=(16, 4), dim_names=('dp', 'tp')
  dim 0 (dp): ranks=16, nodes=8, ppn=2
  dim 1 (tp): ranks=4, nodes=1, ppn=4
```

With the depth-penalized TP scorer, `--max-candidates 2` keeps the 1D baseline
and the TP=4 elbow for this graph, so the capped search still evaluates the
measured best mesh.
